# `mlkem-kat-gen`: `libcrux-ml-kem 0.0.10` Differential KAT Generator

Standalone Rust crate generating the expected `libcrux-ml-kem 0.0.10` outputs and `SHA3-256`
digests checked at compile time by `LibsignalBinary/Proofs/HookDischarge/CryptoMlKem/Spec/MlKemKat.lean`:

1. **Round-3 CRYSTALS-Kyber-1024 (`libcrux_ml_kem::mlkem1024::portable`)**:
   `kyber_generate_key_pair`, `kyber_encapsulate`, `kyber_decapsulate` (honest round-trip and
   corrupted-ciphertext Fujisaki–Okamoto implicit rejection with Kyber's `SHAKE256_32(x || H(ct))` KDF).
2. **Incremental FIPS 203 ML-KEM-768 (`libcrux_ml_kem::mlkem768::incremental`)**:
   `KeyPairCompressedBytes::from_seed`, `validate_pk_bytes` (including header/key length boundaries
   `63`/`64` and `1151`/`1152`, tampered `H(ek || rho)`, and non-canonical `ek` coefficients `3328`
   vs `3329` and `4095` with recomputed matching `SHA3-256(ek || rho)`), `encapsulate1`,
   `encapsulate2` (including non-canonical `es` bytes), and `decapsulate_compressed_key` (honest
   round-trip and corrupted-`ct1` / corrupted-`ct2` FO implicit rejection).

In addition to these vectors, `Spec/MlKemKat.lean` also replays every ML-KEM-768 call vector in
`LibsignalBinary/Proofs/SpqrV1/Vectors/Protocol.lean` (generated by
`third_party/libsignal/libsignal-session/tools/spqr-vectors`).

These vectors come from the implementation the spec models. Official NIST vectors (FIPS 203 ACVP
ML-KEM-768 and the Kyber-1024 Round 3 KAT) are checked separately in `Spec/MlKemOfficialKat.lean`;
see `Spec/official_kat_gen/README.md`.

## Regenerating / Verifying Offline

From the repository root:

```bash
cargo run --release --offline \
  --manifest-path LibsignalBinary/Proofs/HookDischarge/CryptoMlKem/Spec/kat_gen/Cargo.toml
```
